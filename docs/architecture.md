> This document was generated by the automated Architecture Design Doc Generator.

## Overview

**AgenticWorkflows** is a workshop repository that teaches participants how to build and run GitHub Agentic Workflows using GitHub Copilot. The repository ships a deliberately simple ASP.NET Core 10 Minimal API (`AgenticWorkflows.Api`) as a subject codebase so that workshop exercises — such as test-quality checks, documentation-drift detection, and duplicate-code finding — can operate on real, compilable source.

The API manages a lightweight in-memory work-item backlog and is intentionally small so that agentic workflows (automated AI agents triggered by GitHub Actions) can analyze, review, and improve it as workshop exercises.

## HTTP API Endpoints

All work-item routes are grouped under `/work-items` and tagged `Work items` in OpenAPI.

| Method | Path | Description |
|---|---|---|
| `GET` | `/` | Redirects to `/work-items`. |
| `GET` | `/work-items` | Returns all work items ordered by priority (desc) then due date (asc). |
| `POST` | `/work-items` | Creates a new work item; returns `201 Created` or `400 ValidationProblem`. |
| `GET` | `/work-items/summary` | Returns aggregate counts and a health indicator. |
| `GET` | `/work-items/{id}` | Returns a single work item; `404` if not found. |
| `GET` | `/work-items/{id}/notifications` | Returns pre-composed notification strings for a work item; `404` if not found. |

## Component Interactions

```
HTTP Request
    │
    ▼
Program.cs (endpoint handler)
    │
    ├─── WorkItemService ──► IDateProvider (SystemDateProvider)
    │         │
    │         └─── OperationResult<T> (returned to handler)
    │
    └─── NotificationComposer (static, called directly)
```

- **`Program.cs`** acts as the composition root and the thin controller layer; it delegates all logic to `WorkItemService` or `NotificationComposer`.
- **`WorkItemService`** holds the in-memory store (a `List<WorkItem>`) and depends on `IDateProvider` for date-relative validation and seeding.
- **`NotificationComposer`** is a stateless static class that formats notification text from a `WorkItem`.
- **`OperationResult<T>`** wraps success/failure outcomes so endpoint handlers can decide the appropriate HTTP response without coupling to exception-based control flow.

## Design Decisions and Patterns

| Decision | Rationale |
|---|---|
| **Minimal API (no controllers)** | Keeps the surface area small and easy for workshop participants to read in one file. |
| **In-memory store (no database)** | Removes infrastructure concerns so the workshop stays focused on agentic workflows rather than data persistence. |
| **`IDateProvider` abstraction** | Enables deterministic unit tests via `FixedDateProvider` without mocking frameworks. |
| **`OperationResult<T>` result type** | Makes validation failures explicit at the type level and avoids throwing exceptions for expected business-rule violations. |
| **Static `NotificationComposer`** | Notification formatting has no state or external dependencies, so a static class is the simplest fit. |
| **Seeded work items** | Pre-populated data lets participants interact with the API immediately without first creating items. |

## Testing Strategy

The `AgenticWorkflows.Api.Tests` project uses **xUnit** and targets .NET 10.

- Tests exercise `WorkItemService` directly (unit tests, no HTTP layer).
- `FixedDateProvider` pins the current date to `2026-05-31`, making date-sensitive assertions stable.
- The test suite includes both behavior-focused tests (validation rules, trimming, summary counts) and intentionally weak tests (e.g., `Assert_True`) to serve as workshop examples of low-quality test coverage.

No integration tests or HTTP-layer tests are present; the API layer is thin enough that unit testing the service covers the critical logic.
