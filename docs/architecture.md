> **Generated by:** Automated Architecture Design Doc Generator

## Overview

**AgenticWorkflows** is a workshop repository used to teach participants how to build GitHub Agentic Workflows using GitHub Actions, GitHub Copilot, and the `gh aw` CLI. It pairs a deliberately simple ASP.NET Core 10 Minimal API (the "demo app") with a collection of pre-built and learner-created agentic workflows that operate on that app.

The demo application manages a small in-memory work-item backlog and exposes REST endpoints that workshop participants modify, test, and review using automated agentic workflows.

## Components

### 1. `AgenticWorkflows.Api` — Demo REST API

**Location:** `src/AgenticWorkflows.Api/`  
**Framework:** ASP.NET Core 10 Minimal API (.NET 10)

The demo API is the target application that workshop participants change and that agentic workflows inspect. It provides CRUD-like access to an in-memory work-item list.

#### Endpoints

| Method | Route | Description |
|--------|-------|-------------|
| `GET` | `/` | Redirects to `/work-items` |
| `GET` | `/work-items` | Lists all work items ordered by priority then due date |
| `POST` | `/work-items` | Creates a new work item; returns `201 Created` or `422 Validation Problem` |
| `GET` | `/work-items/summary` | Returns aggregate health metrics |
| `GET` | `/work-items/{id}` | Returns a single work item by GUID; returns `404 Not Found` when absent |
| `GET` | `/work-items/{id}/notifications` | Returns pre-formatted created and due-soon notification strings; returns `404 Not Found` when absent |

OpenAPI metadata is exposed at `/openapi/v1.json` in the Development environment.

#### Models

| Type | Role |
|------|------|
| `WorkItem` | Immutable record: `Id`, `Title`, `Description`, `Priority` (1–5), `Status`, `DueDate` |
| `WorkItemStatus` | Enum: `Todo`, `InProgress`, `Done` |
| `CreateWorkItemRequest` | Input DTO: `Title`, `Description?`, `Priority`, `DueDate?` |
| `WorkItemSummary` | Read-only aggregate: totals, overdue count, high-priority count, health label |
| `ValidationError` | Error value object: `Code`, `Message` |

#### Services

**`WorkItemService`** (singleton, in-memory store)

- Holds a `List<WorkItem>` seeded with four demo items at startup.
- Validates `CreateWorkItemRequest` (title length ≤ 80, description length ≤ 240, priority 1–5, due date not in the past).
- Returns `OperationResult<WorkItem>` — a discriminated union of success (with value) or failure (with `ValidationError` collection).
- Computes summary health as "Healthy" when there are no overdue items and at most two high-priority (≥ 4) open items; otherwise "Needs attention".
- Depends on `IDateProvider` to obtain today's date, enabling testability without time-coupled logic.

**`IDateProvider` / `SystemDateProvider`**

- Single-method abstraction (`DateOnly Today`) that wraps `DateOnly.FromDateTime(DateTime.Now)`.
- Injected as a singleton; replaced by `FixedDateProvider` in tests.

**`NotificationComposer`** (static)

- Builds plain-text notification strings for "work item created" and "work item due soon" events.
- Truncates descriptions to 90 characters with an ellipsis.
- Maps integer priority to a human-readable label (Backlog → Critical).

**`OperationResult<T>`** (sealed record)

- Lightweight result type carrying either a value or a list of validation errors.
- `Succeeded` is `true` when the error collection is empty.

## Component Interactions

```
HTTP client
    │
    ▼
Program.cs (Minimal API routing)
    │  reads/writes via
    ▼
WorkItemService (singleton, in-memory list)
    │  uses
    ├─► IDateProvider  (injected; System or Fixed)
    │
    └─► NotificationComposer  (static; called from route handler)
            │  formats
            ▼
         WorkItem (immutable record)
```

The route handlers in `Program.cs` are the only entry points. All business logic lives in `WorkItemService`. `NotificationComposer` is a pure formatting utility with no dependencies.

Dependency injection is configured in `Program.cs`:
- `IDateProvider` → `SystemDateProvider` (singleton)
- `WorkItemService` (singleton, depends on `IDateProvider`)

## Design Decisions and Patterns

| Decision | Rationale |
|----------|-----------|
| Minimal API (no controllers) | Reduces ceremony; keeps the demo surface small and easy to read |
| In-memory list instead of a database | Workshop focus is agentic workflows, not persistence; eliminates infrastructure dependencies |
| `OperationResult<T>` discriminated union | Makes validation failures explicit without exceptions; mirrors railway-oriented patterns |
| `IDateProvider` abstraction | Decouples "today" from `DateTime.Now`, making validation logic fully testable |
| Singleton service lifetime | Acceptable for an in-memory, single-process demo with no concurrent-write concerns |
| Static `NotificationComposer` | Pure formatting logic with no side effects; intentionally shares structure between the two methods to give the Duplicate Code Detector workflow something to find |
| Seeded work items on startup | Gives the API a meaningful initial state without a migration step |

## Testing Strategy

Tests are written with **xUnit** and target `WorkItemService` directly (no HTTP layer). The test suite is intentionally split into two quality levels:

- **`WorkItemServiceTests`** — high-value behavioral tests that verify outcomes: validation errors are returned for invalid input, field values are trimmed, summaries reflect the correct counts.
- **`WeakCoverageTests`** — low-value tests added deliberately as workshop material to demonstrate what the Test Quality Checker agentic workflow is designed to detect and flag.

`FixedDateProvider` provides a pinned `DateOnly` so tests are not affected by the calendar date.

The CI workflow (`ci.yml`) runs `dotnet test` on every push and pull request.
