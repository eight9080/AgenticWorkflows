## Overview

`AgenticWorkflows` is a workshop application that teaches participants how to build and run GitHub Agentic Workflows using GitHub Copilot coding agent, code review, and custom agentic workflow definitions. The repository contains:

- A minimal ASP.NET Core Web API (`AgenticWorkflows.Api`) that serves as a realistic but simple target application for the workshop exercises.
- A suite of agentic workflow definitions (`.md` + `.lock.yml` pairs under `.github/workflows/`) that demonstrate automated code quality, documentation generation, and duplicate-code detection.
- Workshop instructions (`README.md`) and sample workflow starters (`samples/`).

## Major Components

### 1. `AgenticWorkflows.Api` — ASP.NET Core Minimal API

The API is the hands-on code target for all workshop tasks. It manages a simple in-memory backlog of work items.

| Layer | Files | Responsibility |
|---|---|---|
| **Entry point / routing** | `Program.cs` | Registers DI services, maps all HTTP endpoints via minimal-API route groups. |
| **Domain models** | `Models/WorkItem.cs`, `WorkItemStatus.cs`, `WorkItemSummary.cs`, `CreateWorkItemRequest.cs`, `ValidationError.cs` | Immutable records and enums representing work-item data. |
| **Service layer** | `Services/WorkItemService.cs` | In-memory CRUD + validation + health summary. Seeds four demo items on startup. |
| **Notification formatting** | `Services/NotificationComposer.cs` | Static helper that builds human-readable "created" and "due soon" notification strings from a `WorkItem`. |
| **Date abstraction** | `Services/IDateProvider.cs`, `SystemDateProvider.cs` | Thin interface over `DateOnly.Today` so tests can inject a fixed date. |
| **Result type** | `Services/OperationResult<T>.cs` | Discriminated union (success/failure with `ValidationError` list) returned by `WorkItemService.Create`. |

## Component Interactions

```
HTTP Client
    │
    ▼
Program.cs  (route group /work-items)
    │
    ├── GET /work-items          → WorkItemService.GetAll()
    ├── POST /work-items         → WorkItemService.Create()  ──→ OperationResult<WorkItem>
    ├── GET /work-items/summary  → WorkItemService.GetSummary()
    ├── GET /work-items/{id}     → WorkItemService.Find()
    └── GET /work-items/{id}/notifications
                                 → WorkItemService.Find()
                                   NotificationComposer.Build*()

WorkItemService
    └── depends on IDateProvider (injected)
        ├── SystemDateProvider  (production)
        └── FixedDateProvider   (tests)
```

All state is held in a `List<WorkItem>` within the singleton `WorkItemService`; there is no database.

## Design Decisions and Patterns

| Decision | Rationale |
|---|---|
| **Minimal API** (no controllers) | Keeps routing logic visible in one file, making the code easy to inspect during the workshop. |
| **In-memory storage** | Eliminates infrastructure dependencies so the app starts instantly in Codespaces. |
| **`OperationResult<T>`** | Allows `Create` to return structured validation errors without throwing exceptions; maps cleanly to `Results.ValidationProblem`. |
| **`IDateProvider` abstraction** | Enables deterministic unit tests for date-sensitive validation (due-date-in-past) and summary health without mocking the system clock. |
| **`NotificationComposer` as a static helper** | Centralises notification formatting, which the "Duplicate Code Detector" workflow intentionally exercises (the two `Build*` methods share nearly identical structure, a deliberate workshop demonstration target). |
| **Singleton `WorkItemService`** | Appropriate for a stateless demo; all participants share the same in-memory list within a single process run. |
| **Seed data tied to `IDateProvider.Today`** | Due dates are expressed as offsets from today so demos remain valid regardless of when the Codespace starts. |

## API Endpoints

| Method | Path | Response |
|---|---|---|
| `GET` | `/work-items` | `200 OK` — list of all items, ordered by priority desc then due date asc |
| `POST` | `/work-items` | `201 Created` — new item; `400 Bad Request` (validation problem) on failure |
| `GET` | `/work-items/summary` | `200 OK` — `WorkItemSummary` with counts and health status |
| `GET` | `/work-items/{id}` | `200 OK` — single item; `404 Not Found` if absent |
| `GET` | `/work-items/{id}/notifications` | `200 OK` — created + due-soon notification strings; `404 Not Found` if absent |

OpenAPI (`/openapi/v1.json`) is available in the `Development` environment.

## Testing Strategy

Tests live in `tests/AgenticWorkflows.Api.Tests` (xUnit).

- **Behavioral tests** (`WorkItemServiceTests.cs`) cover validation rules, field trimming, summary counts, and health status using a `FixedDateProvider` for date control.
- **Weak-coverage tests** (`WeakCoverageTests.cs`) are intentionally low-value implementation tests used as workshop material for the Test Quality Checker workflow.
- No integration or HTTP-level tests are present; the service layer is tested directly.
