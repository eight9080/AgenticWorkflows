## Overview

AgenticWorkflows is a workshop template repository used to teach participants how to build GitHub Agentic Workflows with GitHub Copilot. It ships a small ASP.NET Core 10 Minimal API (`AgenticWorkflows.Api`) as a concrete, inspectable codebase that the agentic workflows can act on — reviewing tests, detecting duplicate code, and keeping API documentation up to date.

The repository doubles as a live demonstration: participants run coding-agent tasks, Copilot code reviews, and custom agentic workflows against the same application they can read and modify.

## Major Components

### 1. `AgenticWorkflows.Api` — ASP.NET Core Minimal API

The application exposes a simple work-item tracker over HTTP.

#### Models (`Models/`)

| Type | Role |
|---|---|
| `WorkItem` | Immutable record representing a tracked task (id, title, description, priority 1–5, status, due date). |
| `WorkItemStatus` | Enum: `Todo`, `InProgress`, `Done`. |
| `CreateWorkItemRequest` | DTO carrying the fields supplied by the caller when creating an item. |
| `WorkItemSummary` | Aggregated counts (total, open, done, overdue, high-priority) plus a derived `Health` string. |
| `ValidationError` | Code/message pair returned inside a validation problem response. |

#### Services (`Services/`)

| Type | Role |
|---|---|
| `WorkItemService` | In-memory store. Holds the item list, seeds demo data, and exposes `GetAll`, `Find`, `Create`, and `GetSummary`. Validates requests before mutation. |
| `IDateProvider` / `SystemDateProvider` | Abstracts `DateOnly.Today` so tests can inject a fixed date without time-sensitive failures. |
| `NotificationComposer` | Static helper that builds human-readable "created" and "due-soon" notification strings for a given `WorkItem`. |
| `OperationResult<T>` | Generic result envelope: carries the created value on success or a list of `ValidationError` on failure, eliminating exception-based validation flow. |

#### Routes (`Program.cs`)

| Verb & Path | Behaviour |
|---|---|
| `GET /` | Redirects to `/work-items`. |
| `GET /work-items` | Returns all items ordered by priority (desc) then due date (asc). `200 OK`. |
| `POST /work-items` | Creates a new item after validation. `201 Created` or `400 ValidationProblem`. |
| `GET /work-items/summary` | Returns aggregated `WorkItemSummary`. `200 OK`. |
| `GET /work-items/{id}` | Returns the item or `404 Not Found`. |
| `GET /work-items/{id}/notifications` | Returns pre-formatted "created" and "due-soon" notification strings, or `404 Not Found` if the item is absent. |

OpenAPI/Swagger is enabled in the Development environment via `Microsoft.AspNetCore.OpenApi`.

### 2. Tests (`AgenticWorkflows.Api.Tests`)

The xUnit test project exercises `WorkItemService` directly (unit tests). A `FixedDateProvider` is injected so date-sensitive assertions are deterministic. Key covered behaviours:

- Validation rejects blank titles, out-of-range priorities, and past due dates.
- Creation trims whitespace and inserts the item with `Todo` status.
- `GetSummary` counts open, done, overdue, and high-priority items and derives the correct `Health` value.

## Key Design Decisions

### In-memory persistence
`WorkItemService` is registered as a singleton and stores items in a `List<WorkItem>`. This is intentional for a demo application — it keeps the codebase minimal and eliminates database setup friction for workshop participants. State is reset on every application restart.

### Immutable records
All domain types (`WorkItem`, `WorkItemSummary`, `CreateWorkItemRequest`, `ValidationError`) are C# `record` types, enforcing value semantics and immutability after creation.

### `IDateProvider` abstraction
Injecting the current date through an interface is the only test-seam that separates domain logic from the system clock. `SystemDateProvider` is the production implementation; tests use `FixedDateProvider`.

### `OperationResult<T>` envelope
Rather than throwing exceptions for validation failures, `WorkItemService.Create` returns an `OperationResult<T>`. The caller (the Minimal API route) inspects `result.Succeeded` and maps to the appropriate HTTP status code, keeping error handling explicit and avoiding exception-for-flow-control anti-patterns.

### Minimal API (no controllers)
Routes are declared inline in `Program.cs` using the Minimal API model. This reduces boilerplate and keeps the full HTTP surface visible in a single file — useful for workshop demonstrations.

## Testing Strategy

Tests target business logic in `WorkItemService` in isolation (unit tests). Infrastructure concerns — routing, serialisation, middleware — are not integration-tested in the current test suite. The xUnit framework is used with no mocking library; dependencies are replaced by hand-written fakes (`FixedDateProvider`). This approach is deliberately lightweight to serve as a starting point for the Test Quality Checker agentic workflow.
